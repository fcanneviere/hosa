# Hosa Git (Sprint Branch/Worktree Lifecycle Agent) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a new agent, `hosa-git`, that is the sole owner of the managed project's git repository lifecycle for a `Sprint`: it opens a dedicated branch/worktree when a sprint starts, and merges it locally once every ticket in the sprint has a passing QA record. A companion `git` skill lets it be triggered directly; the existing `sprint` and `qa` skills each gain one line offering to hand off into it at the natural moment.

**Architecture:** One new agent (`agents/git.md`) with three input modes — Mode 1 (start a sprint: open branch/worktree), Mode 2 (finish a sprint: QA-gated local merge), Mode 3 (ad hoc git requests). Modes 1 and 2 delegate the actual worktree/merge mechanics to the already-installed `superpowers:using-git-worktrees` and `superpowers:finishing-a-development-branch` skills rather than reimplementing git plumbing — `hosa-git` supplies the sprint-level branch name, reads the `Sprint`/`Ticket`/`Test Plan` KB to decide *whether* a merge is allowed, and writes the resulting `branch`/`worktree`/`state` fields back onto the `Sprint` concept. `hosa-git` is not a numbered pipeline stage — it's transversal, same status as `hosa-documentation`, but with two hot dispatch points (`sprint`, `qa`) instead of zero.

**Tech Stack:** Markdown agent/skill files (Claude Code plugin conventions), no code/tests — this repo's "implementation" is markdown content, verified by grep/read checks, same as the `infra`/`sprint`/`documentation` plans.

**Spec:** `docs/superpowers/specs/2026-09-26-hosa-git-design.md`

## Global Constraints

- New agent frontmatter: `name: hosa-git`, `model: claude-opus-4-8`, `memory: project`.
- `hosa-git` operates exclusively on the managed project's git repository (root path read from `kb/infra/`) — never on `C:\dev\hosa` itself.
- GitHub push/PR is out of scope v1 — the Mode 2 merge is always local (`superpowers:finishing-a-development-branch` forced to its "Merge locally" option, no menu presented).
- `Sprint` (`kb/sprints/<slug>.md`) gains two frontmatter fields written only by `hosa-git`: `branch: sprint/<slug>` and `worktree: <absolute path>` — both added in Mode 1, both removed in Mode 2 on a successful merge (`state` becomes `done` at that point).
- `hosa-git` is the only Hosa agent allowed to commit — only in Mode 2 (the merge commit, via the reused `finishing-a-development-branch` flow) and Mode 3 (ad hoc, only if explicitly requested). Never in Mode 1.
- Every commit `hosa-git` makes uses the user's own git identity only (`git config user.name`/`user.email`, checked first) — never `Co-Authored-By`, never an additional author. This overrides any global default attribution instruction for this repo's work.
- Mode 1 reuses `superpowers:using-git-worktrees` (branch name `sprint/<slug>`); Mode 2 reuses `superpowers:finishing-a-development-branch` forced to "Merge locally" — no reimplementation of worktree creation or merge bash logic in `hosa-git` itself.
- Mode 2 QA gate: for every ticket listed in the `Sprint`, `kb/test/<slug-ticket>-technique.md`'s `## Résultats techniques` must be entirely passed, and its recette result(s) must be `Réussi` or "Non applicable". Any ticket failing this blocks the merge entirely — never a partial merge.
- OKF §9 logging (chronological, most recent date first) to `kb/sprints/log.md` for every state/branch/worktree change `hosa-git` makes.
- No renumbering of the data-structuring pipeline, no new numbered stage — `hosa-git` is explicitly transversal, like `hosa-documentation`.

## Review Focus

- **Mode 1 called on a `Sprint` whose `state` isn't `planned`** (already `active` or `done`). A reasonable person expects it to say so and stop — not silently open a second worktree — unless the request explicitly asks to reattach to an already-`active` sprint's existing worktree. Task 1's Mode 1 steps must state this explicitly.
- **Mode 2 called on a `Sprint` whose `state` isn't `active`, or missing `branch`/`worktree`.** A reasonable person expects "nothing to merge" rather than an attempted merge against a branch that may not exist. Task 1's Mode 2 steps must state this explicitly.
- **Mode 2's QA gate finds one ticket out of several still failing or missing its record.** A reasonable person expects the whole merge blocked and every blocking ticket listed — not a merge that silently drops the failing ticket's work or merges the rest. Task 1's Mode 2 steps must state this explicitly.
- **The reused `finishing-a-development-branch` flow finds tests failing on the merged result.** A reasonable person expects the worktree and branch left in place, `Sprint.state` unchanged (`active`), nothing marked `done` — not a partial state update. Task 1's Mode 2 steps must state this explicitly.
- **`qa`'s Suite line is reached with an unclean verdict** (technical failures or recette to fix still open). A reasonable person expects no offer to merge in that case — merging on a red QA report would just be caught again by `hosa-git`'s own gate, but the skill shouldn't dangle the option regardless. Task 3's `qa` edit must make the merge offer conditional on the clean "Sprint validé." verdict only.

## Good Git Practices (all modes)

- Never commit directly to the base branch while a sprint is `active` — the sprint lives on its own branch until it merges.
- Before any commit you make yourself (only the Mode 2 merge commit, and an explicit ad hoc commit in Mode 3 — never in Mode 1): check `git config user.name`/`user.email` first. Never `Co-Authored-By`, never an additional author.
- Never force-push, never `git reset --hard`, never `git clean -f` without the exact confirmation word the user is asked for — same guard as `superpowers:finishing-a-development-branch`.
- Never merge when tests fail on the merged result, and never merge a sprint with any ticket missing a green QA record (Mode 2 gate below).

## Mode 1 — Start a Sprint

1. Read `kb/sprints/<slug>.md`. If `state` isn't `planned`, say so and stop — no double start — unless the request explicitly asks to reattach to an already-`active` sprint's existing worktree, in which case report the existing `branch`/`worktree` instead of creating anything.
2. Read `kb/infra/` for the managed project's root path. Missing → ask for it rather than guessing.
3. Invoke the `superpowers:using-git-worktrees` skill with branch name `sprint/<slug>`, in the managed project's repository — it handles worktree placement (`.worktrees/`), branch creation, setup, and baseline tests. Don't reimplement this. The explicit request to start this sprint counts as the declared worktree preference — its own Step 0 consent question doesn't need to be re-asked.
4. Write `state: active`, `branch: sprint/<slug>`, `worktree: <path>` into `kb/sprints/<slug>.md`.
5. Log the change to `kb/sprints/log.md`.
6. Report the branch and worktree path — ticket work (via `build`/`iterate`/`test`/`debug`) should now happen inside it.

## Mode 2 — Finish a Sprint (QA-gated local merge)

1. Read `kb/sprints/<slug>.md`. If `state` isn't `active`, or `branch`/`worktree` are missing, say so — nothing to merge — and stop.
2. **QA gate:** for every ticket listed in the sprint, read `kb/test/<slug-ticket>-technique.md`'s `## Résultats techniques` (must be entirely passed) and its recette result(s) (must be `Réussi` or "Non applicable"). Any ticket missing its record, or showing `Échoué`/`Partiel`, blocks the merge: list every blocking ticket and what it's missing, suggest `qa`/`debug`/`hosa-product-owner` as appropriate, and stop — never a partial merge.
3. Everything green → invoke the `superpowers:finishing-a-development-branch` skill, forced to its "Merge locally" option (no menu presented — local-only merge has already been decided for this project): it verifies tests, merges into the base branch, cleans up the worktree, deletes the branch.
4. If that flow reports failing tests on the merged result, or a conflict: stop, report, leave the worktree/branch in place — `kb/sprints/<slug>.md` stays `state: active`. Nothing to write.
5. On success: write `state: done` into `kb/sprints/<slug>.md`, and remove its `branch` and `worktree` fields (the sprint no longer has an active workspace). Log the change to `kb/sprints/log.md`.
6. Report the result.

## Mode 3 — Ad Hoc Git Requests

One-off requests outside a sprint's own start/finish cycle (status, cleaning up an orphaned worktree, undoing a commit...): handle directly, applying the same Good Git Practices above. No KB write for this mode unless the request actually concerns an identified sprint, in which case Mode 1/2 applies instead.

## No Commits (exception assumed)

The only Hosa agent that commits — only the Mode 2 merge commit, and an ad hoc Mode 3 commit if explicitly requested. Never in Mode 1. Always under the user's own git identity, never a co-author — the same core Hosa rule as everywhere else, applied here directly instead of deferred to the user.

# Git

Drives the managed project's git repository lifecycle for one `Sprint` at a time: opening its branch/worktree at the start, merging it locally once its QA is clean.

## Flow

```
Lit kb/sprints/<slug>.md
        ↓
Détermine le mode depuis la requête (démarrage / fusion / ad hoc)
        ↓
Dispatch hosa-git dans ce mode
        ↓
Rapporte le résultat (branche/worktree ouverts, ou fusion/blocage)
```

## Trigger

Manual: `/git demarre <slug>`, `/git termine <slug>`. Auto: "démarre le sprint X", "commence le sprint X" → Mode 1 ; "termine le sprint X", "fusionne le sprint X", "merge le sprint X" → Mode 2.

---

## Step 1: Determine the Mode and Sprint

From the request, determine whether this is a start (Mode 1), a finish (Mode 2), or an ad hoc git request (Mode 3), and which `Sprint` slug it targets. If either is unclear, ask rather than guess.

## Step 2: Dispatch `hosa-git`

Dispatch `hosa-git` in the determined mode with the sprint slug. It reads `kb/sprints/<slug>.md` and the relevant KB, performs the worktree creation or QA-gated merge (or the ad hoc request), and reports back.

## Commits

This skill dispatches the one Hosa agent allowed to commit (`hosa-git`, Mode 2/3 only) — always under the user's own git identity, never a co-author.

## Output

```
[hosa-git's Output Format for whichever mode ran]
```
